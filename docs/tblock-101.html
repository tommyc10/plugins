Principles

Agents and roles

Helpers on a short leash

The main agent owns the task, the playbook and the reply to you. It hands bounded jobs to helpers, each with its own memory and the model its role needs, then reviews their work itself.

delegate

One bounded job
  • Gets a code change or a fix, with the files, what done means, and the check to run.
  • Stays inside those files. Never pushes or posts.
  • Returns a fixed report: changed, checked, not checked, decisions.

threepio

Ticket writer
  • Drafts GitLab or GitHub tickets from the finished work and its checks.
  • Only claims what the diff or the checks back up.
  • Drafts only. A person says yes before anything is created.

Review panels

interrogate · ui-council
  • Reviewers on different model families try to break the change.
  • A finding counts only with proof: a run, a screenshot, or a repro.
  • They report. The main agent re-checks and decides.

Why agents and not just skills

Separate memory

Screenshots and long logs stay in the helper's context. The main thread keeps only the summary.

A different model

A skill runs on whatever model is already running. An agent can run on the model its role needs.

A tighter leash

A helper gets a short brief with hard limits, so it can't spawn its own helpers or push.

The know-how stays in skills

Each agent file is about ten lines that point at a skill, so Copilot and Claude Code share one copy.

What it does without asking, and what it never does alone

Just does it
  • Read and edit code
  • Run builds, tests, the app
  • Local commits on a branch
  • Spawn the helpers a step needs
Always asks first
  • Push or force-push
  • Open, approve or merge a PR
  • Post to chat or tickets
  • Deploy, or delete anything

Build a prompt

State the goal and how to tell it's done. Don't list skills: the playbook already knows them.
Does it use more tokens?

Yes, mostly on helpers and review panels. The efficient preset keeps that down, and for a one-line edit you can skip tblock-mode. A cheap answer that's wrong costs more once you count the fix.

Can it push or deploy by itself?

No. Pushing, PRs, tickets, deploys and deletes always wait for a clear yes, and a yes covers that one action only.

What if my project has no tests?

Its proof is only as good as the checks it can run. It says what it could not check instead of claiming a pass, and it can set up a verification skill for the project.

How do I find the right skill?

Ask /tblock-help. It maps what you want to do onto the skill or playbook that does it, and fixes runs that went wrong.
